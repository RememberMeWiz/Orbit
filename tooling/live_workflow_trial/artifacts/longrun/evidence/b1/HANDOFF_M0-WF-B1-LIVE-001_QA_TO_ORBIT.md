### Claim 1

- **Verdict:** breaks
- **Attack:** The source grep and guard API surface rule out obvious process-termination calls, but they do not prove that every Orbit-controlled UI action is non-terminating. A realistic sequence is: ChatGPT is foreground; Orbit has a guarded geometry-click operation available as a last resort; an update/banner/modal or window-layout change moves controls; Orbit computes or reuses coordinates intended for a benign target; before the click, the UI changes; the same coordinates now land on an in-app control that closes, relaunches, signs out, or otherwise ends the current ChatGPT session. The foreground-window guard still passes because the click remains inside ChatGPT. A post-condition can detect the mistake only after the side effect. A similar indirect path exists if any typed executor outside the grepped driver can invoke an updater/relauncher or if a launch race starts another ChatGPT instance whose own singleton/update behavior disrupts the existing one. The Architecture review correctly preserves the fixed rule that Orbit must never gain terminate/restart authority, but that fixed rule is broader than the evidence currently cited for this claim.
- **Residual risk:** Even if Orbit contains no process-kill primitive, it can still cause session loss indirectly through in-app UI actions, update/relaunch affordances, sign-out flows, stale geometry, or another executor path. “No kill API” is therefore weaker than “cannot end a session.”
- **Required evidence:** Enumerate every Orbit-controlled side-effect path, not only `launch_app` and the guard class. Prove that no executor, UIA action, geometry click, keyboard path, menu action, updater path, or helper can activate close/relaunch/sign-out/update controls. Add adversarial tests where update banners/modals appear, the window resizes, a monitor is unplugged, DPI/layout changes, and UI elements move between targeting and actuation. Geometry fallback should have an explicit denylist/allowlist that excludes window chrome, account/session controls, update/relaunch controls, and unknown modal surfaces. Keep the Architecture constraint unchanged: no terminate, kill, close-window, or automated restart authority.

### Claim 2

- **Verdict:** breaks
- **Attack:** The double `GetForegroundWindow()` check still has a time-of-check/time-of-use gap. Sequence: Orbit verifies target HWND; verifies it again immediately before `SendKeys`; the user alt-tabs, Windows moves focus after a monitor unplug, an update/modal steals focus, or another ChatGPT window becomes foreground in the few instructions between the second check and the actual keyboard injection; `SendKeys` then goes to the newly foreground window. The second check makes the race smaller, not atomic. `Ctrl+A`, `Ctrl+V`, and especially `Enter` can have meaningful side effects in the wrong foreground application.
- **Residual risk:** Any API that injects ordinary keyboard input into the global foreground queue inherits focus-race risk unless target identity and actuation are bound atomically or the operation is replaced by a target-specific semantic action. Two ChatGPT windows make this worse because a wrong target can still look superficially valid.
- **Required evidence:** Run a high-frequency adversarial focus-flipper during every keystroke site and record the actual receiving HWND with an independent low-level keyboard/window hook. Include alt-tab storms, second-window activation, sleep/wake, monitor unplug/replug, update/modal focus steals, and process/window recreation. The acceptance condition is zero keystrokes received by any HWND other than the bound target across a large stress run. Prefer eliminating global `SendKeys` for safety-sensitive actions in favor of target-bound UIA/semantic operations where possible. If keystrokes remain, the safety claim must be weakened unless a mechanism can prove recipient binding at actuation time, not merely immediately before it.

### Claim 3

- **Verdict:** breaks
- **Attack:** A syntactically valid `ORBIT_DIRECTIVE` can itself be prose unless directive provenance is authenticated separately from transcript content. Sequence: a pending `request_id`, work item, and registered endpoint name appear or can be inferred in the conversation; an adversarial message, pasted content, or model response includes a fully filled `ORBIT_DIRECTIVE` envelope quoting that pending request and naming a valid endpoint; the transcript scanner walks newest-first and finds it before the genuine local-program directive; all field-level checks pass; the endpoint resolves uniquely and the `directive_id` is fresh; Orbit acts on content that was only chat prose. Rejecting `<angle bracket>` placeholders, checking registry scope, and consuming `directive_id` once do not establish who authored the directive. The Architecture review’s broader principle that authority must come from a trusted control source, not body text, applies here too.
- **Residual risk:** Prompt injection can manufacture structurally perfect control-looking text. Newest-first scanning increases the chance that a later injected envelope shadows an earlier legitimate one. One-time consumption prevents replay, not first-use forgery.
- **Required evidence:** Prove source provenance. The parser must accept directives only from a trusted local-program channel or from records authentically bound to that channel, never from arbitrary transcript text. Test with user messages, assistant messages, quoted prior directives, code blocks, attachments, copied logs, and nested fake envelopes containing the exact live `request_id`. Evidence should show they are classified as transcript data and cannot enter the directive-consumption path. Also test two ChatGPT windows and transcript accumulation to ensure the accepted directive is bound to the intended session/work item, not merely the newest matching string.

### Claim 4

- **Verdict:** holds conditionally
- **Attack:** The state machine correctly avoids automatic resend after an uncertain post-actuation crash, but the claim still needs a single-writer guarantee. A realistic failure sequence is two Orbit runner instances overlapping after a kill/restart or watchdog race. Both load the same delivery record before either observes the other’s durable transition; both independently stage and actuate the same send; each can then persist a consistent-looking local record. The described `SEND_ACTUATED -> AMBIGUOUS` recovery prevents one runner from resending after restart, but it does not by itself prove that two concurrent actors cannot actuate once each. A second boundary is the external application/network: pressing Enter exactly once does not prove the remote service cannot duplicate submission internally unless a remote idempotency identity exists.
- **Residual risk:** Local intent-before-actuation handles the crash window well, but “nothing external happens twice” is stronger than “Orbit never intentionally auto-resends after uncertain actuation.” Concurrency, duplicate runner ownership, and remote retry behavior remain separate duplication sources.
- **Required evidence:** Demonstrate an OS/process-wide single-writer lock or atomic compare-and-swap around delivery ownership and state transition, surviving restart and stale-process overlap. Stress-test two concurrent runner processes against the same workspace/delivery record and prove exactly one reaches actuation. Kill processes at every state boundary, including immediately before and after Enter. Verify append-only receipts and state transitions remain linearizable. If the remote ChatGPT send path exposes no idempotency key/receipt capable of proving remote exactly-once semantics, narrow the claim to the property actually guaranteed: Orbit does not automatically re-actuate an ambiguous delivery.

### Claim 5

- **Verdict:** breaks
- **Attack:** The observed behavior during Architecture review was safe, but the general claim is not established while guarded geometry click exists. Sequence: Orbit targets a benign in-app control using screen coordinates; ChatGPT is foreground, so the foreground guard passes; between coordinate selection and click, the app updates, a modal appears, the composer disappears, DPI/layout changes, the user moves/resizes the window, or a second monitor is unplugged; the coordinates now land on `Continue with Work?` or another confirmation button; Orbit clicks it. The post-condition may reveal that the intended action did not occur, but the confirmation has already been granted. This failure stays entirely inside the correct foreground ChatGPT window, so the foreground guard does not protect against it. The fact that the current confirmation prompt exposes no accessibility control is useful for that exact prompt state, but it is not a durable safety boundary across app updates.
- **Residual risk:** Geometry is positional, not semantic. Any same-window UI change can transform a previously safe coordinate into an approval, destructive, or authority-expanding control. A future ChatGPT version may also expose the confirmation to accessibility, changing today’s “no accessible control” fact.
- **Required evidence:** Treat confirmation surfaces as a prohibited action class, independent of accessibility exposure. Before any geometry click, prove the selected window, layout generation, target rectangle, and absence of modal/confirmation surfaces are still the same immediately at actuation; then verify the actual hit target semantically where possible. Better, restrict geometry fallback to a tiny allowlist of non-authorizing controls and categorically refuse clicks whenever an unknown modal, approval prompt, permission prompt, update dialog, account control, or blocking overlay is present. Test with synthetic modals appearing between target acquisition and click, monitor unplug, DPI changes, window movement, update banners, and composer removal. A post-condition alone is insufficient because approval is irreversible once clicked.

### Claim 6

- **Verdict:** breaks
- **Attack:** The evidence only shows that Orbit does not deliberately scrape specific credential stores/fields. It does not prove that secrets cannot appear in data Orbit already reads. Sequence: the user pasted an API key, password-reset link, private token, SSH material, or other secret into a ChatGPT conversation; Orbit reads that transcript into local state; a later dispatch, summary, artifact, clipboard payload, or cross-chat handoff includes transcript-derived content; Orbit pastes/sends it through ChatGPT. The secret has now left the machine even though Orbit never extracted a cookie or `session_id`, and the endpoint registry itself remained clean. The registry grep protects registry metadata, not transcript-derived payloads, generated artifacts, clipboard contents, logs, crash evidence, or outbound model/chat text.
- **Residual risk:** Secrets are content, not just credential-field names. They can exist in prose, code blocks, filenames, stack traces, environment-variable dumps, pasted logs, local file content, or generated artifacts. Local-state persistence also creates a secondary secret-retention surface even before egress is considered.
- **Required evidence:** Define the actual egress surfaces and scan them, not only the registry. Seed unique canary secrets into transcript prose, code blocks, filenames, clipboard state, local artifacts, error messages, and any allowed file-read path. Exercise normal dispatch, failure, retry, STOP/resume, crash recovery, logging, artifact creation, and cross-chat delivery. Prove canaries do not appear in any network-bound payload, destination chat, telemetry, crash report, or unintended artifact. If Orbit intentionally sends transcript-derived user content to ChatGPT, the absolute claim “no secrets leave the machine” is not supportable without a content-classification/redaction boundary; the claim should instead state the narrower property that Orbit does not extract or transmit protected credentials except through explicitly authorized user-content paths.

## Highest-Priority Gap

**Fix the keystroke recipient race first.**

Claim 2 is the most exploitable on a real desktop because the required trigger is ordinary behavior, not a crafted protocol attack: alt-tab, a focus-stealing update/modal, sleep/wake, window recreation, or monitor changes can all occur naturally in the tiny interval between the second foreground check and `SendKeys`.

The consequence is immediate. `Ctrl+A`, `Ctrl+V`, or `Enter` landing in the wrong foreground application can overwrite text, paste sensitive content, or submit an unintended action before Orbit has any opportunity to recover. The current double-check reduces probability but does not eliminate the race.

The first remediation should therefore be to remove global foreground-dependent keystrokes from safety-sensitive paths wherever a target-bound semantic operation is available, and to build an instrumented adversarial focus-race test that records the true receiving HWND for every injected key. Until that test demonstrates recipient binding under aggressive focus churn, the claim should not be stated as absolute.

This ranks above the geometry-confirmation gap because the keystroke path is exercised by normal delivery behavior and can escape the intended application entirely. The confirmation-click gap is the next priority because same-window geometry races can grant authority after layout changes.
