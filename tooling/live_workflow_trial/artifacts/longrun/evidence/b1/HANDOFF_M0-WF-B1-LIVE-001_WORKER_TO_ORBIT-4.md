## Summary
Make the race deterministic with a harness-only start gate immediately before the production mutex wait. Each runner signals that it has reached the gate. Only after all four are present does the controller release them simultaneously. Whichever runner acquires the mutex first signals a harness observation point and is deliberately held inside the critical section for a short interval so that the other three are actually waiting on the mutex rather than merely starting later. The pause is test instrumentation only; mutex acquisition, ledger reads, transitions, and actuation remain production code.
Run 5,200 trials: 1,000 ordinary tight races with no crash; 1,000 crashes after durable SEND_ACTUATED but before Send; 1,000 crashes after external Send actuation but before SENT_UNCONFIRMED is persisted; 1,000 crashes at randomized points while the mutex is held; 1,000 slow-holder/writer-busy/abandoned-mutex recovery trials; and 200 cross-session races using two Windows logon sessions if the claim really means the whole Windows installation rather than one logon session. If the production mutex is not machine-global across sessions, the claim must instead say "same Windows logon session."
A runner that loses the mutex race must wait through the real production timeout behavior. A timeout must result in writer-busy and process exit or equivalent stop behavior; it must never become permission to take over while the holder is alive.
For the first boundary, install a harness observation hook immediately after the SEND_ACTUATED transition has completed its durable write, including the production flush/commit operation, and immediately before the Send actuator is entered. The holder blocks there. The controller verifies that the durable state is visible on disk, then calls TerminateProcess. The fake target must show zero Send actuations. A waiter must receive abandoned-mutex ownership, reload the latest disk state after acquiring it, and must not actuate Send.
For the second boundary, let Send occur. The independent fake target first durably records the button actuation. The runner then stops at a harness hook after the actuator returns but before the SENT_UNCONFIRMED durable write. Once the controller has independently observed the target-side Send record, it calls TerminateProcess. The next runner must acquire the abandoned mutex, reload from disk, observe that the record is already at the pre-Send durable boundary, and must not Send again. The independent actuation count must remain exactly one.
For the general mutex-abandonment case, also kill a holder immediately after successful mutex acquisition but before its first delivery-record read. That makes it easy to detect a bad takeover implementation that continues from stale in-memory state. Randomized critical-section trials should additionally kill after the first disk read, around durable transition boundaries, and while the holder is paused in the actuation window.
Separately test the slow-but-alive case without killing the holder. Pause the holder inside the critical section for longer than the configured waiter timeout. Every waiter must report writer-busy and stop; none may acquire or actuate. Then release the original holder and let it finish. In another variant, allow all current waiters to time out, then TerminateProcess the still-owning holder and start a fresh runner. Only that fresh runner may receive abandoned ownership. This distinguishes legitimate Windows abandonment from an invented time lease.
Graceful shutdown belongs only in control trials: a cooperatively stopped holder should release the mutex normally, and the next runner should see ordinary acquisition rather than abandonment.
The fake target's button handler is the independent actuation meter. Every actual Send-button invocation appends one record to a target-owned journal containing trial ID, delivery-record ID, target process ID, a monotonic sequence number, and timestamp. The fake target flushes that journal before acknowledging the actuation. The target process and its journal must be outside Orbit's ledger/state directory and remain alive when a runner is killed.
For trial t, define A_t as the number of target-journal Send events carrying that trial's delivery-record ID. A_t, not Orbit's SENT/SEND_ACTUATED state, is the duplicate-send oracle.
Keep separate harness tracing for mutex and recovery sequencing. It should record runner PID, mutex wait result, acquisition time, whether acquisition was normal or abandoned, every post-acquisition disk-read revision, transition revision, actuator entry/exit, and process termination. That trace can be produced by observation hooks around production operations, but it must never replace those operations. In particular, after WAIT_ABANDONED the first record state used for a transition must come from a disk read performed after that acquisition. If the recovered runner transitions using a revision it read before acquiring the mutex, the trial fails even when A_t happens to be zero or one.
max(A_t for t = 1..5200) <= 1
and equivalently the aggregate duplicate excess must satisfy:
sum(max(0, A_t - 1) for t = 1..5200) = 0.
The scenario-specific oracle should be stronger where the injected boundary makes the expected count known. Ordinary no-crash races must finish with A_t = 1. Kill-after-durable-SEND_ACTUATED-before-Send trials must have A_t = 0. Kill-after-Send-before-SENT_UNCONFIRMED trials must have A_t = 1. Slow-holder trials in which the original holder is eventually released normally must have A_t = 1. Random crash trials may legitimately end at zero or one depending on the kill point, but never above one.
Duplicate count is not the only pass criterion. Define D_t = 1 if the trial deadlocks or fails to produce either a completed result or an explicit writer-busy/recovery result within a harness watchdog period after all intentional test gates have been released. The watchdog is only a test failure detector; it grants no takeover authority. Define R_t = 1 if an abandoned-mutex acquirer performs a transition without first reloading the latest persisted record revision after acquisition. Define U_t = 1 if, after the crash phase, a clean fresh runner cannot move the record to a documented terminal state or explicit non-actuating reconciliation/human-action state and instead leaves it permanently in an internal state that no subsequent clean runner will resolve.
The harness passes only if:
sum(D_t + R_t + U_t for t = 1..5200) = 0
in addition to the actuation inequality above.
A deadlock is therefore failure even with zero duplicate Sends. A waiter treating timeout as takeover is failure. WAIT_ABANDONED followed by use of stale memory is failure. A record stranded forever after the pre-Send crash is failure even though A_t = 0. A post-Send crash that causes a second Send is an immediate failure.
The fake target proves how often participating Orbit runners invoke the local Send actuator. It does not prove that the real ChatGPT renderer, UI Automation stack, network layer, or remote service will convert one local button invocation into exactly one remote message. A real UI could itself mishandle one invocation, and the server could retry or deduplicate independently. Those are outside this claim.
TerminateProcess exercises abrupt process death and Windows mutex abandonment, but it is not equivalent to sudden power loss, kernel crash, storage-controller cache loss, or filesystem corruption. If crash-consistency across machine power failure is desired, it needs a different durability test and should not be implied by this result.
The guarantee applies only to participating Orbit runners that use the same mutex protocol and the same ledger. An old runner build, a manually launched tool, another program, or malicious software that ignores the mutex is outside the guarantee. Likewise, a Windows named mutex coordinates only the kernel namespace in which it exists. If Orbit has not demonstrated a Global mutex and usable ACLs across Windows user sessions, "same Windows installation" is too broad and should be narrowed to "same Windows logon session." A named mutex also cannot coordinate another physical machine or VM, even if both point at a shared file.
Finally, the harness is empirical adversarial evidence over 5,200 forced interleavings, not a mathematical proof of every scheduler ordering. The defensible wording remains: Orbit guarantees at-most-once local Send actuation per delivery record among participating Orbit runners that share the production ledger and named-mutex domain on the same tested Windows scope. It should not be shortened to "Orbit sends each message exactly once."
